## 1. R1：读取/消费审计的坐标与次数

### 1.1 修的是什么

| 上一轮实现 | 本轮实现 |
| --- | --- |
| `prefetch_report` 用 `range(windows_expected)` 推算已消费位置 | 记录**实际**交付/完成的位置序列（按 batch 顺序） |
| worker 事件里的 index 是底层 split 位置，而 sampler position 是 `IndexSubset` 槽位 | 加载器统一用 `PositionView`：`__getitem__` 直接接收底层位置，`len()` 仍返回整个 split 长度以保持冻结噪声规则 |
| 消费集合用 `set`，重复读取 / 多 epoch / 多 condition 被吞掉 | 身份 `(phase, key, position)`，按 key 分别聚合，digest 用**多重集**，重复可数 |
| worker 全部记成 `main` | `worker<id>@pid<pid>`，父进程为 `main@pid<pid>` |
| 只区分"读过" | 区分 `delivered`（loader 交付）与 `completed`（该批训练步跑完），异常中断留痕 |

### 1.2 关键实现点

- `WorkerAuditDataset` 的 `phase` / `key` 在**建 DataLoader 之前**写入，随 pickle 进入 worker，
  因此每条事件自带 epoch 或验证条件身份；
- `ConsumptionLog` 在消费者**取下一批**时才把上一批记入 `completed`，所以异常退出会留下
  "已交付未完成"，完整遍历则 `delivered == completed`；
- `LoaderAudit` 按 `(phase, key)` 保存真实读取序列、打开事件、交付/完成序列、worker 进程集合、
  loader 生命周期与队列排空失败数；`payload()` 同时给出旧字段名（`opened_files`、
  `windows_by_file`、`windows_read`、`open_events`）；
- 原始有序消费写入 `loader_consumption.csv`（`phase,key,position,delivered_index,completed`）。

### 1.3 证据

- 真实 2-worker smoke（`rework1/smoke_parallel2`）训练 phase：
  `reads.windows_read = 40`、`unique_positions = 40`、`duplicate_reads = 0`、
  `consumed.windows_completed = 40`、`unconsumed_reads = 0`、`unread_consumed = 0`、
  `aborted = false`、`exhausted = true`、`batches_completed/batches_delivered = 10/10`、
  worker 键形如 `worker0@pid22676`；验证缓存 phase 四个 condition 各 16 窗、共 64 窗，
  同样零未消费、零未读；
- `loader_consumption.csv` 104 行（训练 40 + 验证缓存 64），与核验器独立复算的计划
  完全一致（见 R2 的 L2 检查）；
- 单元测试 `test_stage1_loader_optimization`：29 项通过，其中新增
  非连续子集、跨 epoch 同位置、四 condition、异常中断、worker 分组、CSV 往返等 12 项针对
  上述缺陷的回归；
- 上一轮"完整 epoch 最后天然有预取剩余"的说法被实测否定：完整遍历时未消费读取为 **0**。

`epoch_mid` 采样在计时区间内，折算到约 5.8 s 的 epoch 可忽略。
**这些数字只描述父进程（训练循环解释器）**，不代表 worker 进程内存，更不代表整机内存；
字段与 JSON 的 `memory_sampling.not_measured` 都写明了这一点。

**R1 原测（历史版本）**，run `bench-20260927T114431Z`，`rework1/benchmark/`：

| num_workers | 窗/秒（均值±SD） | 相对 0 | 每 epoch loader 等待（同步诊断） | 前端 | fwd+bwd | optimizer | 逐批输入摘要一致 | 读取/完成/未消费 | 父进程读取 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **0** | **8.35 ± 0.28** | 1.000 | 4.69 s | 0.098 s | 0.201 s | 0.074 s | 基准 | 288/288/0 | 288 |
| 2 | 6.57 ± 0.11 | 0.786 | 6.03 s | 0.087 s | 0.151 s | 0.074 s | 是 | 288/288/0 | 0 |
| 4 | 4.62 ± 0.07 | 0.552 | 9.01 s | 0.086 s | 0.167 s | 0.073 s | 是 | 288/288/0 | 0 |

**新旧比较**：0 worker 的均值差 1.0%（8.27 vs 8.35，R2 的 SD 更大：0.69 vs 0.28，
最小轮 7.29 窗/s），2 worker 差 0.02%，4 worker 差 3.4%；三档排序与倍率量级一致
（R2 ×1.000 / ×0.794 / ×0.539 对 R1 ×1.000 / ×0.786 / ×0.552），
因此**速度结论不变**：`num_workers=0` 最快，多读者变慢。R1 该 run 的三档 `memory` 是 `{}`，
已作为历史版本原样保留，不改写、不删除。

父进程线程取默认（10）复测 run `bench-20260927T114758Z`（R1 脚本版本、流水口径，见
`rework1/benchmark_threads_default/`）：8.30 / 6.65（×0.801）/ 4.67（×0.563）窗/秒，结论相同；
该次同样没有可用的内存记录（R2 未复测默认线程档，内存结论以 R2 的 threads=2 run 为准）。

关掉 worker 事件流的诊断 run `bench-20260927T115149Z`（`rework1/benchmark_diagnostic_no_audit/`）
为 8.45 / 6.56 / 4.60 窗/秒，与开启事件的 8.35 / 6.57 / 4.62 几乎一致，即身份审计的成本约 **1%**，
不是变慢的原因。该诊断配置没有任何读取证据，**不得**当作可接受的吞吐配置。

**逐批数据摘要的单独开销**（R4 要求"置于计时外或明确单列开销"）：摘要在计时循环内执行
（保证三个配置跑的是同一段代码），其成本单独实测于
`benchmark/digest_cost.json`（`scratch/measure_digest_cost.py`，真实窗张量、12 窗 3 批 ×5 次重复）：

| 项 | 数值 |
| --- | --- |
| 每批 `tensor_digest(signals) + tensor_digest(labels)` | **23.8 ms**（21.7–28.7 ms） |
| 折算到本基准的 48 窗 epoch（12 批） | **0.285 s** |
| 占 0-worker epoch wall（5.752 s） | **4.96%** |

即绝对窗/秒被摘要压低约 5%；它对 0/2/4 三个配置完全相同，因此**不改变**相对结论。
正式训练不计算该摘要（只在等价对照脚本里开启），所以真实训练吞吐略高于基准绝对值。

### 4.3 如何解读（区分已证实与假设）

- **已证实**：在本机、本盘、这份 gzip 分块 HDF5 数据上，多读者并行**降低**端到端训练吞吐；
  worker 越多越慢；逐批输入与串行逐位相同。每 epoch 的 loader 等待随 worker 数上升，说明变慢
  发生在数据到达环节，而不是模型或前端。
- **未证实（假设，需专门实验）**：为什么多读者更慢。最可能是多个进程对同一批 gzip 压缩块
  并发读取，把原本较连续的读取变成交错随机读；进程启动与队列 IPC 也有成本。本轮的证据只能
  支持"数据到达变慢"，不能定量拆分磁盘随机化与 IPC 各自占多少。
- **未测**：9590 窗整轮、SSD 副本、网络盘、更大的 batch。
- `nvidia-smi` 只作为可选瞬时采样记录在主 run 里（计时区间外：训练前 12%、训练后 6%），
  它不是本轮任何结论的依据；报告中的忙占比一律指 CUDA event 口径。
- 上一轮 ×1.176 的差异来源已定位到方法：那次测的是 `inference_mode` + `eval` 的前向循环，
  GPU 每批负担更轻、且没有逐区域同步语义；它的报告数字与自身 CSV 也不一致，因此不能作为
  真实训练收益的依据。
- **推荐**：正式训练保持 `num_workers=0`（也是默认值，旧调用语义不变）。若以后要再试并行，
  应先做"同一文件多读者 vs 单读者"的磁盘级实验，而不是继续调 worker 数。

## 7. 仍存在的限制

1. 性能结论是**有界样本**（48 窗 × 2 epoch × 3 迭代，单机单盘）。它足以分辨 0.79×/0.55× 这种量级，
   但不足以给出整轮定标；整轮 9590 窗未测。
2. 并行审计的身份证据依赖"父进程消费日志 + worker 事件"，两者都在本进程/本机内；
   若 worker 崩溃在事件入队之前，核验器能发现"已消费未读到"（P5/unread_consumed），
   但不能证明崩溃前的物理读取次数。
3. 历史两份 smoke 的具体差异无法逐行还原（旧版本源码已被覆盖），本轮只证明该对照无效。
4. 真实模式下 0/2/4 workers 的训练轨迹在本机逐位相同；这不等于在别的 GPU / 驱动 / 机器上
   也逐位相同，脚本内保留 `--deterministic` 与逐批摘要以复检。
5. `nvidia-smi` 利用率只有计时区间外的两次瞬时采样，不足以作为利用率结论；
   报告一律使用 CUDA event 忙占比并写明其自定义口径。
6. 本轮未启用 `num_workers>0` 于任何正式训练；seed 2026 / 2027 产物、G 盘数据、冻结划分未改。
7. **内存口径只覆盖父进程**（R2 按 Codex 裁决不做 worker/进程树汇总）：`parent_*` 是训练循环解释器
   的 working set / OS 峰值，读法为 MiB；它不含 DataLoader worker 进程，也不等于整机内存，
   不能用来回答"这次训练总共占多少内存"。若以后需要 worker 内存证据，应另立任务并单独验收
   （本机 `.venv\Scripts\python.exe` 是 venv 转发器，worker 真正干活的是它的子进程，
   直接枚举"直接子进程"只会读到几 MiB 的转发器外壳）。
