## 1. 结论摘要（先说结果）

1. **优化没有被应用到已验收或已完成的正式训练**。seed 2026 已验收产物未动；seed 2027
   的 5 轮全量训练**全程使用旧的串行加载器**（`num_workers=0`）。本文所有加速数字都
   来自独立基准，不是这两个正式运行的成绩。
2. 在真实冻结数据上、同一样本顺序下的**最佳实测配置是 2 个 worker 且父进程
   `torch` CPU 线程降到 2**，端到端吞吐 **9.12 → 10.72 窗/秒（×1.176）**，
   两次独立测量同向（×1.179、×1.176），逐批张量逐字节等价。
3. **4 个 worker 没有收益**（×0.988），2 个 worker 也只在降低父进程线程占用后才有
   收益。原因不是并行方案写错，而是瓶颈在数据格式本身：见第 3 节。
4. GPU 忙占比只有 **8%–10%**（用 CUDA event 实测）。也就是说，即使加上这 1.18×，
   GPU 仍大部分时间在等 CPU——要真正解决等待，需要改数据格式或做特征缓存，
   这超出本任务授权，已按任务书要求上报由 Codex 决策。

## 2. 做了什么

### 2.1 新增模块与开关

| 文件 | 作用 |
| --- | --- |
| `dronerfa_baseline/stage1_loader_optimization.py` | 独立加载优化模块：`LoaderConfig`、并行/串行两条路径、worker 读取审计、等价性工具 |
| `dronerfa_baseline/benchmark_stage1_io.py` | 有界真实基准（0/2/4 workers），训练进行中会拒绝启动 |
| `dronerfa_baseline/probe_stage1_window_cost.py` | 单窗分段成本探针（HDF5/RMS/AWGN/前端/模型） |
| `dronerfa_baseline/test_stage1_loader_optimization.py` | 19 项等价性/审计/回收测试 |
| `dronerfa_baseline/test_stage1_parallel_audit.py` | 12 项并行审计核验测试（含负向对照） |
| `run_stage1_12drones_training.py` | 新增 `--num-workers`、`--prefetch-factor`；默认仍为 0（旧调用语义不变） |

训练协议保持不动的部分：1M 非重叠 RF0 I/Q 窗、512/256 STFT、ResNet18 二分类、
batch 4、Adam 1e-3、类别加权 CE、AMP fp16、5 epoch、训练噪声档位、
验证噪声种子 12026、固定零门限判决、只按四条件 pooled BA 均值选轮次。

### 2.2 worker 与 epoch 状态

- 使用 **非持久化 worker**：每个 epoch 在 `set_epoch` 之后**重建**加载器，因此
  `seed + epoch*len(dataset) + position` 的噪声规则在每个 worker 里都拿到当前 epoch，
  不依赖持久 worker 的跨 epoch 状态更新。
- Windows `spawn`；每个 worker 独立懒打开自己的 HDF5 句柄，不继承父进程句柄。

### 2.3 读取审计（重点，因为这里原本有个真问题）

串行时父进程确实打开了每个文件，旧审计成立。并行时**父进程一个文件都没打开**，
旧 `read_audit.json` 必然是空的——此时核验器的 C1/C3（"打开的文件恰好是 train+val"、
"审计自述与复算一致"）会**空过**，把"零读取"当成合格。这正是任务书禁止的
"把推算数伪装成实际读取"。

因此：

- worker 侧记录**真实**的文件打开与成功读取事件（读取成功后才发事件），经队列汇总到父进程；
- 新增 `loader_read_audit.json`，按**阶段**切分：验证缓存阶段、训练阶段各自一份，
  而不是混在一起（混在一起时两阶段会显示相同的文件数与窗数——这一点是在真实并行
  smoke 里发现并修掉的）；
- 审计额外给出**预取但未消费**的窗数与示例，不把预取读取冒充成模型见过的数据；
- 核验器新增并行分支（`verify_parallel_loader_audit`，检查 C6–C11），断言：
  并集恰好等于冻结 train+val、**不得出现任何 development_test\* 文件**、
  验证缓存阶段恰好每窗每条件一次、训练阶段读取数不低于消费预算（允许预取上界）、
  每个 epoch 的噪声派生都出现过、worker 事件零丢失。

真实 4-worker smoke 的审计结果：训练 40/40 窗、验证缓存 64/64 窗、测试角色 0 文件、
`drain_failures=0`，与串行真值一致。

### 2.4 等价性

同一 seed、同一 epoch、同一窗顺序下，`num_workers` 0 / 2 / 4 的**预处理后输入张量
逐字节一致**（SHA256 of raw float32 buffer），标签与批内顺序一致；覆盖 2 个 epoch、
两个类别、不同噪声抽取，并用"epoch 1 vs epoch 2 必须不相等"作为反向对照。
另外并行 smoke 的验证缓存 `feature_sha256` 与串行 smoke **四项完全相同**
（`472be5d3…`、`e5934d08…`、`068f9a09…`、`ba5fdec6…`）。

## 3. 瓶颈在哪（为什么简单并行收益有限）

`probe_stage1_window_cost.py` 在同一批窗上分段计时（单窗毫秒）：

| 阶段 | spread（epoch 乱序式跳读） | contiguous（同文件顺序读） |
| --- | --- | --- |
| HDF5 读取（解压+拷贝） | **163.7 ms** | **119.2 ms** |
| + RMS 归一化 | 20.5 ms | 20.8 ms |
| + 复数 AWGN | 7.6 ms | 6.8 ms |
| + STFT 前端（GPU 冷启动含在其中） | 29.6 ms | 5.7 ms |
| + ResNet18 前向 | 30.6 ms | 3.2 ms |
| **合计** | **252 ms（3.97 窗/秒）** | **179 ms（6.43 窗/秒）** |

根因（直接读 G 盘 `T0000_D00_S0000.mat` 得到）：

```
RF0_I: shape=(1, 150000000) dtype=float64 chunks=(1, 8191) compression=gzip compression_opts=3
RF0_Q: 同上
```

即 **float64 存储 + 每 8191 点一个 chunk + gzip 级 3**。一个 1M 窗需要在 CPU 上解压
每通道约 122 个独立 gzip chunk，两通道原始 16 MB。这解释了全部现象：

- HDF5 读取占单窗总成本的 **47%–65%**，是最大单项；
- 这部分是 CPU 上的 zlib 解压，**加 worker 只能并行化解压，不能消除它**；本机 16 逻辑核
  同时还要供父进程 STFT/模型使用，于是线程超额认购，收益被吃掉甚至转负（4 workers ×0.99）；
- 把父进程 `torch` 线程从默认 10 降到 2，给 worker 让出 CPU，2 workers 才稳定出现 ×1.18；
- GPU 忙占比 8%–10%，与"GPU 在等 CPU"一致。

分段探针里 spread 布局的前端/模型耗时明显高于 contiguous，是因为每个布局的第一批
含有 CUDA 冷启动（cuDNN 算法选择、内核编译），12 窗样本太小、被摊薄得不够；
这部分数字不能当作稳态 GPU 成本。HDF5 与 RMS/AWGN 两项不受此影响。

## 4. 实测性能（真实 G 盘数据，同一窗与顺序）

条件：冻结训练划分，96 个窗（两类均衡、跨文件），父进程 `torch` 线程 2，
每配置 warm 重复 4 次、配置间交替以避免缓存/温度漂移；`num_workers=0` 为参考。

| num_workers | warm 窗/秒（均值） | 标准差 | 冷启动窗/秒 | 相对 0 workers | 逐窗等价 | GPU 忙占比 | 单轮 loader/前端/模型 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 0 | 9.12 | 0.16 | 8.91 | 1.000 | 基准 | 8.0% | 8.96 / 0.170 / 0.821 s |
| **2** | **10.72** | **0.10** | 10.80 | **1.176** | 通过 | 9.8% | 6.84 / 0.459 / 0.595 s |
| 4 | 9.01 | 0.23 | 9.08 | 0.988 | 通过 | 8.4% | 8.37 / 0.569 / 0.342 s |

对照与不确定性：

- 同一配置在较小样本（48 窗）上测过两次：2 workers 分别得 ×1.179 与 ×0.905；
  96 窗样本两次都得 ×1.176。**48 窗的抖动大到足以把结论翻转，只有 96 窗结果可信**。
- 冷启动（首次触碰这些窗，页缓存冷）比 warm 略慢，差距不大；本机无法从 Python 侧
  清空系统页缓存，因此"冷"只是"本次运行首轮"，不代表真实冷盘。
- 未做：把几十 GB 原始数据复制到 SSD、全量特征缓存（会冻结随机噪声）、加大 batch。
  这三项按任务书要求留给 Codex 决定。

```
python run_stage1_12drones_training.py --training-seed <seed> --num-workers 2
# 并把父进程 torch 线程数降到 2（基准里的 --threads 2 等价物），
# 否则 16 核上的线程超额认购会吃掉收益
```

## 7. 限制与风险

1. 基准是**有界样本**（96 窗），不是整轮 9590 窗；它足以分辨 ×1.18，但不足以给出精确定标。
2. 单机单盘，未验证多盘/网络盘；`spread` 布局的跳读成本与文件系统页缓存强相关。
3. 等价性测试用的是**小合成 HDF5 夹具**（真实 worker 进程、真实 AWGN、真实 STFT），
   加上真实数据上的缓存哈希对照；没有在 9590 窗全量上做逐窗 0-vs-2 对比。
4. 审计的"预取但未消费"在 epoch 结束时会天然非零（最后的预取批次），这是真实语义，
   不是泄漏；验证缓存阶段按设计每窗每条件读一次，其预取计数不参与通过判定。
5. 未安装 `nvidia-ml-py`，GPU 利用率改用 CUDA event 实测（只能反映"GPU 在算"的时间占比，
   不等于 `nvidia-smi` 的利用率定义）。
